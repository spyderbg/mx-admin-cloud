# Claude Code Implementation Assignment: Multi-Agent Project Development Framework

> **Purpose:** Implement a reusable, project-aware multi-agent development workflow in the **existing repository**, based on `agents_init.md`. This document is an execution specification for Claude Code, Codex, or another authorized coding agent—not a request to replace the existing application.
>
> **First action:** Inspect the repository and produce a short discovery report before making structural changes. Do not assume directory names, interfaces, or endpoints exist until verified.

## 1. Mission and Non-Negotiable Rules

Build a framework in which **Backend**, **CLI**, and **Frontend** agents can work independently, exchange work through a shared coordination mechanism, and safely resume blocked tasks when dependencies are finished. Support both (a) **scoped multi-agent execution** and (b) **authorized full-project execution** by one agent such as Claude Code or Codex. Keep the framework reusable for additional projects without forcing them into this project's specific layout.

### Mandatory constraints

1. **English only:** All agent prompts, generated documentation, GitHub issue/PR templates, code comments added by this work, commit messages, help text, and other agent-generated prose MUST be in English. Do not translate pre-existing user-facing content as part of this task unless explicitly requested.
2. **Centralized agent documentation:** Place **all new documentation generated by agents** under the repository-level `docs_agents/` directory. Do not create new documentation trees elsewhere. Preserve every existing `README.md` and do not delete, relocate, or overwrite it. If an existing README needs correction, propose a narrowly scoped update and obtain authorization if it lies outside the agent's write scope. New comprehensive documentation belongs in `docs_agents/`.
3. **Per-service backend documentation:** Every discovered backend service MUST have its own `docs_agents/backend/services/<service-id>/README.md` and `docs_agents/backend/services/<service-id>/openapi.yaml`. Each service README must explain its purpose, responsibilities, workflows, relevant API endpoints, `ServiceProvider`-based interface/contract, and all actual implemented providers. Do not invent providers or endpoints.
4. **CLI uses APIs:** All CLI functionality that corresponds to backend capabilities MUST use documented, supported backend APIs, **not direct imports or calls into backend service/business logic**. Identify gaps in available APIs and create Backend-owned dependency issues rather than bypassing this rule. Existing code may require a migration plan.
5. **Scoped writes, shared reads:** Scoped agents may modify only the code and tests they own, plus their **allocated** documentation paths. All agents may read shared documentation and create/update authorized GitHub coordination issues. A cross-scope change requires a task for the owner or an explicitly authorized full-project session.
6. **Full-project mode remains possible:** An authorized Claude Code or Codex session must be able to work across Backend, CLI, Frontend, shared coordination, and documentation when requested. Do not construct architectural, file permission, or prompt restrictions that permanently prevent this.
7. **Tests belong to owners:** Each implementation agent writes, runs, and repairs tests for its own area; CI independently validates changes. Do not describe work as verified unless checks actually ran and passed.
8. **No destructive shortcuts:** Do not rewrite major modules, remove working features, disable tests, bypass security, or introduce unnecessary tools/frameworks merely to match a proposed design.
9. **Review before merge:** Agents may prepare PRs; automatic merging into protected branches is **disabled by default**. Never expose secrets or run untrusted repository code with production credentials.
10. **Source of truth:** Existing repository behavior, tests, `ServiceProvider` abstractions, and valid API schemas take precedence over assumptions in this assignment. Record discrepancies and propose a safe migration.

## 2. Begin With Repository Discovery (Required)

Before implementation:

- Identify repository root, top-level components, package/build systems, test commands, CI configuration, GitHub remotes, and existing agent instructions (`CLAUDE.md`, `AGENTS.md`, etc.).
- Determine the **actual** locations of backend services, `ServiceProvider` classes/interfaces, provider implementations, CLI commands, frontend code, and tests. If some components live in other repositories, document the boundaries and access requirements; do not fabricate local paths.
- Inspect backend route declarations and generated OpenAPI sources; classify public, internal, deprecated, and authentication-dependent endpoints.
- Inventory existing `README.md` files and preserve them. Identify existing documentation that should be indexed without moving it.
- Identify how the CLI calls the backend today; flag any direct business-logic coupling.
- Identify frontend network and cache layers, cache invalidation behavior, and user-help rendering.
- Inspect GitHub Issues, labels, existing PR practices, and CI permissions **only when access is available**; otherwise document setup steps and continue with local implementation.
- Check the existing test baseline **before** changing code; record failures that already exist.

Deliver `docs_agents/discovery/README.md` with an inventory, verified paths, constraints, baseline results, and decisions needing clarification. Generate `docs_agents/architecture/README.md` with an architecture map and migration proposals. Do not launch a mass refactor during discovery.

## 3. Execution Modes and Agent Contracts

| Mode | Write permissions | Expected use |
| --- | --- | --- |
| `scoped:backend` | Verified backend code/tests; `docs_agents/backend/**` | Implement services, APIs, providers and backend tests. |
| `scoped:cli` | Verified CLI code/tests; `docs_agents/cli/**` | Implement API-driven CLI parity and CLI tests. |
| `scoped:frontend` | Verified frontend code/tests; `docs_agents/frontend/**` | Implement UI, assets, caching and frontend tests. |
| `scoped:coordination` | Explicitly assigned workflow/configuration files; `docs_agents/coordination/**` | Maintain orchestration adapters, labels, policy, and templates. |
| `full-project` | Explicitly authorized repository scope, subject to safety and review gates | Cross-cutting refactors, whole-project work, end-to-end implementation. |

`full-project` is a **permission profile**, not a separate mandatory AI provider. The same Claude Code or Codex agent may use any mode. Default to scoped mode for delegated tasks and require explicit task metadata or operator approval for `full-project`. Shared read access is always allowed; shared documentation **writes** are assigned by subtree owner to avoid conflicts.

Create a versioned, human-readable project configuration template (e.g. `docs_agents/coordination/project-config.example.yaml`) defining component roots, service discovery overrides, tests, documentation owners, issue repository, execution mode defaults, and optional additional components. Treat this as an example, not evidence that those paths exist. Avoid hardcoding the current project's names.

## 4. Backend Agent Specification

**Ownership:** backend implementation, backend tests, and `docs_agents/backend/**`.

Responsibilities:

1. Implement and maintain backend services, supported API endpoints, the existing `ServiceProvider` contracts, and provider implementations using repository conventions.
2. Preserve the existing provider abstraction. Inspect the real interface before documenting or refactoring; record abstract methods, type signatures, dependency injection / registration, lifecycle, selection behavior, errors, and supported implementations.
3. Produce and maintain one service documentation directory per **actual** backend service:
   - `README.md`: purpose and use cases; boundaries; configuration (redacted examples only); public versus internal operations; lifecycle/data flow; `ServiceProvider` interface methods and their meanings; an accurate provider inventory with implementation paths, capabilities, constraints, and selection/registration behavior; examples; error behavior; testing commands; relevant dependencies; links to API contract.
   - `openapi.yaml`: accurate OpenAPI 3.x specification for HTTP operations belonging to the service, with paths/methods, parameters, request/response schemas, auth requirements, status codes, and examples when useful. Derive from source/generated schema and validate. Avoid duplicate/contradictory endpoint definitions across service files.
4. If a backend service exposes **no HTTP API**, still create `openapi.yaml` as a **valid OpenAPI document with an empty `paths` object**, explicitly document that no HTTP endpoints exist, and document its internal interface in the README. Never invent a route solely to populate the file.
5. Expose backend capabilities through properly authorized APIs when the CLI needs them. A missing route is a backend-owned task and must be reviewed for security and compatibility.
6. Write and validate service-level unit tests, API contract tests, and integration tests as applicable. Confirm generated docs match the actual API.
7. When done, publish completion evidence and unblock dependent CLI/frontend tasks through the coordination workflow.

**Do not:** edit CLI/frontend code in scoped mode; falsely label internal APIs as public; leak service secrets into schemas or documentation.

## 5. CLI Agent Specification

**Ownership:** CLI implementation, CLI tests, and `docs_agents/cli/**`.

Responsibilities:

1. Inventory currently supported backend operations and their authorized API endpoints. Maintain a coverage matrix mapping `backend capability -> endpoint -> CLI command -> tests` in `docs_agents/cli/README.md`.
2. Make **every supported and CLI-appropriate backend function** accessible from the command line through its documented API. For operations that are unsafe, internal-only, asynchronous, or unsuitable for direct CLI exposure, record the justification and a safe proposed alternative; do not silently omit them.
3. Keep command names, options, input formats, output formats, error codes, and authentication consistent with the existing CLI conventions.
4. Give every command and option precise, useful `--help` descriptions, including required/optional arguments, defaults, expected values, API behavior, examples, and failure modes where appropriate.
5. Use a backend HTTP/API client layer. Do **not** import or directly invoke backend `ServiceProvider`s, database access, service registries, or business operations. Shared schema-only libraries are allowed only if they do not bypass the API boundary.
6. Test request payloads, authentication handling, validation/error translation, success responses, help output, and command exit codes (mocked API tests plus integration tests where feasible).
7. If an API is missing, create a Backend-labeled GitHub Issue with explicit endpoint requirements, set the CLI task to `blocked`, and resume only when the dependency has demonstrably been completed.
8. Generate **user-oriented documentation only**, under `docs_agents/cli/`. Do **not** generate a separate technical API specification for CLI; link to the backend's canonical `openapi.yaml` instead.

**Do not:** alter backend/frontend code in scoped mode or implement private backend logic inside the CLI.

## 6. Frontend Agent Specification

**Ownership:** frontend UI/client code and assets, frontend tests, and `docs_agents/frontend/**`.

Responsibilities:

1. Own the presentation of project capabilities, including layouts, components, interaction flows, accessibility, responsiveness, and integration with supported backend APIs.
2. May create or update necessary frontend-owned images, sound files, and other presentation assets. Use approved asset-generation tools, follow licensing and repository asset conventions, and avoid unrelated modifications.
3. Inspect and implement appropriate backend-response caching. Define cache keys, normalized identity, TTL/staleness policies where appropriate, invalidation on mutations, optimistic updates/rollback as applicable, auth-scoped caching, and safe handling of errors and concurrent requests. Prefer the existing frontend data-fetching library and patterns rather than introducing a second cache system.
4. Maintain user-facing help/documentation in Markdown or another **source-controlled format suitable both for code review and for rendering within the application**. Store its authored source under `docs_agents/frontend/`; implement a safe app-side reader/rendering integration if needed. Ensure links and image paths work and do not expose internal-only information.
5. Write and run frontend-only unit/component tests; add integration or end-to-end tests for critical flows and cache invalidation when supported by the project.
6. Report missing or mismatched backend APIs through Backend-owned issues and wait for dependency completion instead of editing backend implementations in scoped mode.
7. Can read all `docs_agents/**` content but may update only `docs_agents/frontend/**` unless assigned cross-scope ownership.

**Do not:** edit backend/CLI implementation or other components' documentation in scoped mode.

## 7. Shared Coordination via GitHub Issues

GitHub Issues is the **proposed** cross-agent work queue. Use GitHub through approved integrations (`gh` or API) when credentials/permissions exist. Provide templates and setup instructions when credentials are absent; do not claim a live integration was tested.

Create `docs_agents/coordination/README.md`, an issue template, a PR template, and a configurable label/status convention. Suggested labels:

- Ownership: `agent:backend`, `agent:cli`, `agent:frontend`, `agent:coordination`, `agent:full-project`.
- State: `ai:proposed`, `ai:ready`, `ai:in-progress`, `ai:blocked`, `ai:review`, `ai:done`, `ai:failed`.
- Optional: `ai:needs-human`, `priority:high`, `priority:medium`, `priority:low`.

Use one current state per issue. Keep issue bodies structured:

- Goal and business rationale.
- Owning component/agent and proposed execution mode.
- Reproduction/current behavior (if relevant).
- Acceptance criteria and explicit out-of-scope items.
- API/documentation contract impact.
- Test plan and expected evidence.
- Dependencies using GitHub issue references (not prose alone).
- Linked branch/PR and completion evidence.

**Dependency protocol:**

1. A working agent discovering cross-component work creates or updates an issue for the **owning** agent, avoiding duplicates.
2. Record dependency issue IDs and mark the caller task `ai:blocked`; persist a compact resumable handoff with the exact missing contract and work already completed.
3. The owning agent selects ready tasks, works in its allowed scope, and publishes test evidence, documentation changes, and a PR.
4. A dependency is considered satisfied only when its acceptance conditions are met and the required integration state is available (e.g. merged API or specifically approved integration branch); **PR creation alone does not automatically unblock downstream work**.
5. Scheduler/agent checks dependency status, safely refreshes its worktree/branch, resumes work, and re-runs relevant integration tests.
6. Handle dependency cycles, duplicate tasks, races, stale locks, and blocked tasks explicitly. Human escalation is required for unresolvable cycles or disagreements.

Prefer pull-based task claims with durable issue references, a lease/lock or equivalent race-prevention mechanism, explicit timeout/retry budgets, and an auditable activity log. Never run two agents concurrently against the same writable checkout. Use isolated branches/worktrees or containers, and reconcile overlapping PRs intentionally.

### README preservation and discoverability

- Keep existing README files **at their original locations** and preserve existing content. No automatic cleanup or wholesale replacement.
- Create a navigable `docs_agents/README.md` index linking to existing READMEs (without copying or relocating them), to each component guide, and to the service catalog.
- If GitHub-native templates must physically exist under `.github/` to function, treat them as **workflow configuration files**, not free-standing documentation: make the smallest authorized configuration change needed and keep their canonical descriptive content in `docs_agents/coordination/templates/`. Record this exception explicitly. Never claim a template is GitHub-active while it exists only in `docs_agents/`.
- Document generation should be repeatable, idempotent, and non-destructive. Add a validation step to detect undocumented services, stale provider lists, broken links, and OpenAPI drift.

## 9. OpenAPI and ServiceProvider Accuracy Gates

For each discovered backend service:

- Identify canonical code location, API router(s), route prefix(es), lifecycle, `ServiceProvider` declaration(s), provider implementations, registry/selection logic, and corresponding tests.
- Prefer extraction from the actual framework-generated OpenAPI schema, where available. Partition endpoints by explicit ownership; retain accurate shared schemas/security references or bundle them in a valid standalone document.
- Validate the per-service YAML with a suitable OpenAPI parser/validator. Reconcile duplicates and avoid publishing undocumented internal details in public-oriented examples.
- Check every named provider against actual code or verified registration/configuration; distinguish implemented, optional, disabled, and planned providers.
- Document differences between provider methods and public HTTP operations; the `ServiceProvider` contract is **not automatically an HTTP API**.
- Add or update relevant tests or validation scripts in the backend's permitted area and document exact commands/results.

## 10. Implementation Plan: Incremental Delivery

### Phase 0 — Baseline and architectural decisions

**Tasks:** complete discovery; record repository topology and existing README index; establish exact agent ownership paths; inspect current API, CLI, frontend, test, and GitHub setup.

**Deliverables:** `docs_agents/discovery/README.md`, initial `docs_agents/architecture/README.md`, issue list of uncertain/missing prerequisites.

**Exit gate:** paths and test commands are verified; pre-existing failures and unresolved cross-repo access are explicit.

### Phase 1 — Shared documentation foundation

**Tasks:** create `docs_agents/README.md` and component indexes; establish directory ownership conventions; build a service/provider inventory from code; create per-service `README.md` and valid `openapi.yaml` documents without changing behavior.

**Deliverables:** complete service documentation tree, link index, documented generation and validation commands.

**Exit gate:** every backend service inventoried; existing READMEs intact; OpenAPI docs validate; no invented routes/providers.

### Phase 2 — Coordination and safe agent execution

**Tasks:** add GitHub labeling and issue/PR/handoff templates, dependency state model, ownership configuration, task-claim protocol, blocked/unblocked workflow, and safe worktree isolation. Implement the smallest viable coordinator using existing tooling before introducing a new daemon. Distinguish documentation/templates from activated GitHub configuration.

**Deliverables:** coordination guide, project configuration example, tested task-state transitions and setup scripts/configuration where appropriate.

**Exit gate:** two agents can coordinate a simulated cross-component dependency without unauthorized writes, duplicate claims, or silent loss of progress.

### Phase 3 — Backend ownership and service contract validation

**Tasks:** implement agreed backend changes only where supported by the discovered gaps; document providers and endpoints; add missing coverage and contract validation. Create backend tasks for CLI-required endpoints rather than allowing bypasses.

**Deliverables:** accurate backend service docs, relevant tests, any necessary narrowly scoped PRs.

**Exit gate:** service contracts match runtime and relevant backend CI checks pass.

### Phase 4 — CLI API parity

**Tasks:** generate coverage matrix, implement missing API-driven commands, improve `--help` and parameter descriptions, add tests. Issue and wait on any missing backend API dependencies.

**Deliverables:** CLI user guide and verified capability matrix under `docs_agents/cli/`; CLI implementation and tests.

**Exit gate:** all in-scope backend capabilities are CLI-addressable via API or have documented, approved exclusions; help and integration tests pass.

### Phase 5 — Frontend presentation, caching, and user help

**Tasks:** verify API integration, improve frontend-owned presentation/assets as required, implement/test correct cache invalidation, add user-help content in a source format rendered by the application.

**Deliverables:** frontend help and cache policy docs under `docs_agents/frontend/`, relevant UI/tests, setup instructions.

**Exit gate:** frontend tests and representative mutation/invalidation flows pass; generated help renders safely; no cross-scope changes.

### Phase 6 — Full-project agent mode and end-to-end validation

**Tasks:** demonstrate that an authorized single agent can traverse the complete project and implement a controlled cross-cutting task without breaking scoped-agent ownership defaults. Validate full task lifecycle: issue -> claim -> dependency -> implementation -> documentation -> CI -> review -> PR -> completion.

**Deliverables:** reusable onboarding procedure for a future repository; example configuration; final verification report under `docs_agents/`.

**Exit gate:** both scoped and full-project execution are demonstrated, and no merge-to-main occurs without the configured human approval.

**Phase discipline:** Finish and report each phase before proceeding to major refactors. Work may proceed in parallel only for non-overlapping owned paths with independently validated prerequisites. If a phase requires external credentials or approval, complete local deliverables and report what remains blocked.

## 11. Testing, Security, and Acceptance Criteria

### Minimum verification

- Existing test suite baseline captured; new failures investigated.
- Backend service unit/integration/contract tests run as applicable.
- CLI tests verify API-only behavior, success/failure paths, exit codes, and `--help` output.
- Frontend tests verify rendering and network cache invalidation after create/update/delete operations, including auth-boundary behavior.
- YAML OpenAPI validation, README link checks, provider inventory checks, and documentation tree checks pass.
- Cross-component tests verify issue creation, dependency blocking/unblocking, and isolated workspace ownership.
- A full-project agent can intentionally work across components when explicitly authorized.
- CI runs without hardcoded credentials, secret leakage, automatic protected-branch merges, or uncontrolled write access.

### PR readiness checklist

A PR is **ready for human review** only when it includes:

1. Linked issue and acceptance-criteria checklist.
2. Summary of implementation and exact changed component paths.
3. Tests executed, commands, and actual pass/fail results (do not imply omitted checks passed).
4. Updated `docs_agents/` documentation and, for backend services, accurate `README.md` / `openapi.yaml`.
5. API compatibility or migration notes if relevant.
6. Known limitations and any unresolved dependencies.
7. CI evidence and explicit confirmation no unauthorized cross-scope files changed.

Use bounded retries. If a required check fails or cannot be run, mark the task blocked/needs human and **do not** misrepresent the PR as complete or verified. Do not auto-merge.

## 12. Reuse Across Future Projects

Treat the agent coordination model as an adaptable framework:

- Discover component boundaries rather than requiring `backend/`, `cli/`, and `frontend/` literal directory names.
- Allow project configuration to enable/disable components and specify alternative roots, languages, CI platforms, and providers.
- Keep generic workflow guidance separate from project-specific service catalogs.
- Make multi-repository support an explicit documented extension, not an unverified default.
- Prefer existing GitHub, CLI, test, and CI tooling; avoid adding paid services or persistent infrastructure unless justified.
- Ensure every new project can bootstrap `docs_agents/` documentation without overwriting existing README files.

## 13. Instructions to the Executing Agent

Execute this assignment as an engineer working in a live repository:

1. **Start by inspecting**, not assuming. Read `agents_init.md` when available, the repository's existing guidance, and relevant code/tests.
2. Produce the Phase 0 discovery documents first. Explain any unclear ownership, service structure, or repository boundaries before invasive changes.
3. Draft a prioritized list of **concrete, repository-specific implementation tasks** with verified file paths, dependencies, and acceptance criteria. Include it in `docs_agents/coordination/README.md` or a linked file under that subtree.
4. Implement the smallest useful end-to-end increment. Follow the scoped ownership policy unless explicitly instructed to operate in `full-project` mode.
5. For each completed task: update owned documentation, run relevant tests, capture outcomes, and prepare a PR when GitHub access is available and quality gates pass.
6. When an owned task needs another component: create or prepare the cross-agent issue, record the dependency, **stop at the boundary**, and resume after verified completion.
7. Never claim external GitHub actions, pipeline results, deployment, or successful integration unless confirmed by tool output.
8. Finish each work session with a concise report: implemented changes, changed files, tests/results, documentation updated, issues/PRs created (or not created), blocked work, and the next highest-priority action.

### Definition of Done for This Assignment

The repository has a discoverable `docs_agents/` hierarchy; backend service READMEs and validated OpenAPI documents accurately describe existing code and `ServiceProvider` implementations; the CLI follows backend API boundaries and documents command help; the frontend has tested, well-documented cache behavior and app-renderable user guidance; GitHub-based agent handoffs have explicit ownership and dependency rules; existing READMEs remain intact; and both scoped multi-agent and authorized whole-project workflows can be used without bypassing quality or security checks.

> **Do not fabricate completion.** When repository access, credentials, tests, or an actual component are missing, record precisely what was inspected, what remains unknown, and the next concrete step.
